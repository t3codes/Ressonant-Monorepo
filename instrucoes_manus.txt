# Papel e Objetivo
Você é um Engenheiro de Software Sênior especialista em arquitetura Python (FastAPI), monorepos com `uv workspace` e testes automatizados. Sua missão é auditar, refatorar, estruturar para escalabilidade e validar com **evidências reais de execução** o backend de um SaaS que unifica mensageria (estilo Slack), gestão de projetos (estilo Jira/Kanban), calendário (estilo Google Agenda) e gestão de arquivos com permissões (estilo Google Drive).

# Regras Inegociáveis (Zero Inferência)
1. **Proibido presumir ou simular:** Não invente outputs de terminal, não assuma que uma rota funciona apenas lendo o código e não entregue código sem execução real.
2. **Evidência obrigatória:** Toda rota corrigida ou validada deve ter seu comando de teste e o respectivo payload/status HTTP de resposta registrados no relatório final.
3. **Preservação de Contratos:** Não altere os contratos atuais (schemas Pydantic, URLs, métodos HTTP) a menos que haja um bug estrutural grave. Se alterar, documente o motivo e atualize a collection do Postman correspondente.

# Plano de Execução Passo a Passo

## Passo 1: Auditoria de Arquitetura (Monorepo `uv workspace`)
- Analise a raiz do projeto, os arquivos `pyproject.toml` (raiz e pacotes) e a estrutura de `apps/` e `packages/` (libs compartilhadas).
- Avalie se a separação de responsabilidades está profissional e escalável para receber novos apps no futuro (ex: workers, novos serviços).
- Garanta que configurações, logs, schemas base e clientes externos fiquem isolados nas libs compartilhadas e não acoplados dentro do app FastAPI.

## Passo 2: Preparação de Infraestrutura (S3 e Datadog)
- **AWS S3:** Implemente o módulo/cliente de integração com S3 (usando `boto3` ou `aioboto3`) na lib compartilhada para o módulo de arquivos/Drive. Ele deve aceitar `AWS_S3_ENDPOINT_URL` via variável de ambiente para funcionar tanto com AWS real quanto com emuladores (LocalStack).
- **Datadog (Telemetria):** Estruture a instrumentação de APM, logs e métricas (`ddtrace` / `datadog`) nas libs compartilhadas, mas controle sua ativação estritamente via *feature flag* (`DD_TRACE_ENABLED=false` por padrão no `.env.example`). Quando desabilitado, não deve gerar erros nem overhead na aplicação.

## Passo 3: Revisão Funcional e WebSockets
- Inspecione todos os domínios: Autenticação/Equipes, Mensagens, Projetos/Kanban, Agenda e Drive/Permissões.
- **Mensageria em Tempo Real:** Garanta que o fluxo de mensagens entre equipes e usuários opere via **WebSocket** (com gerenciamento de conexões/salas e persistência no PostgreSQL).

## Passo 4: Testes Reais End-to-End (Sem Mocks)
- Suba a aplicação conectada a uma instância real do PostgreSQL.
- Use as collections do Postman presentes no repositório como guia de fluxos e payloads.
- **Rotas HTTP:** Teste **100% das rotas** usando `curl` (ou script automatizado executando `curl`), validando criação, leitura, atualização, deleção e regras de permissão.
- **Rotas WebSocket:** Como o `curl` não sustenta sessões WebSocket bidirecionais, execute um script de validação real (via `websocat` ou script Python usando `websockets`) provando conexão, envio e recebimento de mensagens entre dois clientes.
- Sempre que encontrar um erro (500, 422 inesperado, falha de query, problema de permissão), corrija o código, aplique migrations se necessário e **re-teste até obter sucesso**.

# Entregáveis Finais
1. **Relatório de Auditoria e Evidências:** Lista de melhorias feitas no monorepo, bugs encontrados/corrigidos e os logs reais dos testes (`curl` e WebSocket) comprovando que tudo funciona.
2. **Arquivo `.zip` Completo:** Gere o arquivo `.zip` contendo o monorepo limpo (sem `.venv`, `__pycache__` ou arquivos temporários), com `.env.example` atualizado e pronto para rodar.
